Current Frontend Risk

vocabulary/index.vue 过重

一个文件同时承担分页、训练模式、过滤、音频、进度保存、后端同步和 UI 渲染。后续再加入“同义词辨析入口”，会让主页面更难维护。

这一页强调前端的定位。它不是简单页面，而是资料、练习和同步逻辑混在一起的应用。最需要注意的是词汇主页面已经变厚，后续新增功能前应该先拆组件和 composable。

Backend Architecture04 / 11
Data Flow

当前数据流：静态词库 与用户进度分离

设计结论

第一阶段不要把 3600+ 词库整体迁移到后端。新功能用 word_id + word + chapter_name 关联静态词库，后端只存扩展数据和用户管理数据。

这一页是关键。要解释为什么不建议现在迁移词库。词库迁移会牵动音频路径、前端页面、搜索、练习逻辑。更稳的做法是继续让词库留在前端，把同义词辨析作为扩展表挂上去。

Risk Register

后续开发前的阻塞风险

中文编码混乱

README、注释、页面文案、后端接口说明出现乱码。未来同义词标签和中文辨析内容会直接受影响。

API 地址写死

前端直接写死远程地址 http://110.40.139.199:8000，本地、Docker、生产环境切换不可靠。

数据库迁移缺口

当前主要依赖 create_all。新增同义词表、标签表、关联表时，需要 Alembic 管理结构演进。

构建产物混入仓库

dist、node_modules、__pycache__、Cordova platforms 等让源码边界不清，影响评审和维护。

这一页不展开太细，但要让听众理解：这些不是洁癖式重构，而是会直接影响同义词系统的质量。特别是中文乱码和数据库迁移，都是一旦叠加功能后修复成本更高的问题。

同义词辨析系统的目标架构

辨析组主表：标题、说明、章节、来源、是否公开、归属用户。

API Blueprint

接口设计要避免逐词请求

# Synonym management
GET    /api/synonyms
GET    /api/synonyms/{set_id}
POST   /api/synonyms
PUT    /api/synonyms/{set_id}
DELETE /api/synonyms/{set_id}

# Word relation lookup
POST   /api/synonyms/lookup
body: { word_ids: [72, 73, 74], words: ["deteriorate"] }

# Import for batch authoring
POST   /api/synonyms/import
body: [{ title, tags, rows: [{ word, core_feature, phrases, definitions, examples }] }]

为什么要 lookup 批量接口

词汇页一屏可能有几十个单词，如果逐个请求，会让页面变慢，也会给后端制造不必要压力。

为什么要 import 接口

同义词辨析的内容生产量远大于代码量。没有导入能力，后续维护会被手工录入拖慢。

这一页讲 API 关键取舍。不要为了方便在前端循环请求。也要提前支持导入，因为同义词辨析是内容密集型功能，单纯页面手填会很痛苦。

Roadmap

建议按两阶段推进

阶段 目标 交付物 预计时长
Phase 0 项目地基优化 编码修复、环境变量、Alembic、仓库清理、词汇页拆分计划 3 到 5 天
Phase 1 同义词系统 MVP 后端表/API、展示页、管理页、词汇入口、JSON 导入 7 到 11 天
Phase 2 增强体验 批量编辑、导出、公开共享、更多筛选、内容质量流程 按需求拆分

验收标准

第一版完成时，用户能创建辨析组、添加多个单词、打标签、查看对比表，并能从词汇页或搜索页直接跳转，刷新后数据不丢失。

这里给出可执行排期。Phase 0 是为了降低返工，Phase 1 才是功能开发。不要把 Phase 2 的增强体验混入第一版，否则范围会膨胀。

Decision

先稳住地基
